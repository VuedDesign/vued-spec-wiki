# Figma 图层结构与机器可读性规范 0.1

> ⚠️ **状态：草稿。** 本页从面向设计师的 DOM 科普材料中提炼原则，用于指导后续的 Figma 审核、生成和结构规范建设。当前仅为知识与方向性约定，**尚未形成可执行的插件规则，不参与生产校验**。

## 一、适用范围与术语边界

本页同时适用于 Ctrip 与 Trip 两个 App，讨论的是 Figma 文件自身的结构质量，不定义任何品牌视觉值。

### 1. Figma 图层树

指 Figma 文件中由 `Document`、`Page`、`Frame`、`Group`、`Component`、`Instance`、`Text` 等节点形成的父子结构。Figma 插件审核与生成操作的对象是这棵节点树。

### 2. 浏览器 DOM

指 HTML 被浏览器解析后形成的 Document Object Model。它由 HTML 元素、文本和属性等节点组成，可被浏览器脚本、自动化工具和 AI Agent 读取与操作。

### 3. 二者关系

Figma 图层树可类比为“设计稿的 DOM”，但两者不是同一种技术对象：

- Figma 审核插件读取的是 **Figma 图层树**；
- 网页还原度检查与浏览器 Agent 读取的是 **浏览器 DOM / Accessibility Tree**；
- D2C 的任务之一，是把 Figma 图层树翻译为合理的浏览器 DOM 与样式结构。

## 二、核心原则

### 原则 1：图层结构是设计意图的一部分

AI 和插件不仅读取最终画面，也读取节点类型、父子关系、组件身份、变量绑定、文本内容和图层名称。视觉相同但结构不同的两个设计稿，机器可能得到完全不同的理解结果。

### 原则 2：优先使用官方组件

需要表达按钮、标签、Logo、输入框等明确语义时，应优先调用官方 Figma 组件，而不是用矩形、文字和图标手工拼出“看起来相似”的图形。

官方组件能够向审核与生成系统提供稳定的组件身份、变体、属性和版本关系；手绘复刻通常只能提供视觉近似，缺少可靠语义。

### 原则 3：用 Frame 与 Auto Layout 表达真实布局关系

容器和布局结构应尽量反映内容间的真实关系，包括排列方向、间距、对齐、内边距和自适应行为。避免只为视觉定位而堆叠无意义容器。

### 原则 4：图层与组件需要语义化命名

命名应帮助人和机器理解节点角色。`Button/Primary`、`Price`、`Hotel-Card` 等名称比 `Group 237`、`Rectangle 12` 更具机器可读性。

但命名不是唯一可信身份。插件归属判定应优先使用官方组件身份、Variable Collection 或正式标记，再使用名称与关键词作为辅助特征。

### 原则 5：减少无意义嵌套

重复、空白或只承担无效包装作用的 Group / Frame 会增加节点数量、上下文长度和结构歧义。设计文件应保留对布局、语义或交互真正有价值的层级。

### 原则 6：组件、实例与变体应表达真实状态

重复出现且具有统一规范的对象应组件化；状态差异应优先通过 Variant / Component Properties 表达，而不是复制多个互不关联的图层组。

### 原则 7：审核与生成共用同一结构语义

- 审核系统读取节点树，判断现有设计稿是否符合结构和视觉规范；
- 生成系统写入节点树，创建 Frame、Instance、Text，并绑定组件、变量与状态；
- 生成结果应能被同一审核系统再次识别和校验，形成“生成 → 审核 → 修复”的闭环。

### 原则 8：结构与视觉采用双通道理解

仅凭节点树可能无法判断视觉氛围、遮挡和真实渲染效果；仅凭截图又无法可靠判断组件身份、变量绑定与父子关系。高准确率审核和生成应结合：

- **结构通道**：Figma 图层树及节点属性；
- **视觉通道**：设计稿截图或渲染结果。

## 三、面向 LLM 的图层树处理流程

完整 Figma 文件可能包含大量节点和无关属性，不应未经处理直接作为 LLM 上下文。建议采用以下流程：

1. **清洗**：剔除不可见、锁定后无关、空白或不参与当前任务的节点；
2. **压缩**：合并无意义包装层，只保留必要父子关系；
3. **序列化**：将树转换为带层级、节点类型和稳定引用的结构化文本或 JSON；
4. **语义保留**：优先保留组件身份、变量绑定、文本、交互状态、可见性和布局属性；
5. **按任务裁剪**：审核颜色时不必携带全部动效属性，审核结构时也不必携带与结构无关的完整视觉数据。

## 四、审核与生成的建议归属判定顺序

插件识别节点属于哪个规范时，建议按可信度由高到低使用以下证据：

1. 官方组件身份或组件 Key；
2. Figma Variable / Variable Collection；
3. 插件写入的共享归属标记；
4. 可复现的结构签名；
5. 组件名、图层名与父级名称；
6. 视觉近似、色值或文本关键词。

低可信度证据不应单独触发高影响自动修改。节点 ID 不应写入长期规范，因为它只对应特定文件或特定时刻，无法稳定复用。

## 五、对设计师的当前建议（非插件强制规则）

- 使用官方组件，不手绘已有组件；
- 使用 Frame / Auto Layout 表达布局关系；
- 给关键容器、组件和文本图层使用有语义的名称；
- 使用组件实例和变体表达重复对象与状态；
- 绑定官方 Variables / Styles，而不是只填写相同的原始数值；
- 清理无意义嵌套、空图层和废弃隐藏层；
- 保证生成稿仍可被审核插件识别，而不是只追求视觉相似。

## 六、待团队确认后才能转为插件规则的事项

原始材料没有给出以下精确标准，当前不得由 AI 自行补值：

1. 最大允许嵌套层级，以及超限后的严重程度；
2. 无意义 Group / Frame 的可执行判定条件；
3. 图层、组件、Variant 和 Variable Collection 的统一命名格式；
4. 哪些类型的容器必须使用 Auto Layout；
5. 各官方组件的名称、组件 Key 与允许变体；
6. 哪些属性必须绑定 Variable / Style；
7. “手绘复刻组件”的结构签名和识别阈值；
8. error / warning / suggestion 的分级口径；
9. 哪些问题可以一键修复，哪些必须人工确认；
10. Figma 图层树的清洗、压缩和序列化字段白名单。

上述事项确认后，应把每条规则改写为明确的 `target + 条件 + 严重程度 + 报错文案 + 修复动作`，通过回归测试后再将 `figma_plugin_active` 改为 `true`。
